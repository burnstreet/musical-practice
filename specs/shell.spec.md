# Shell

Lit root element `<gu-app>`. Routes by hash. German, `lang="de"`.

```ts { .api }
export type Route = '#/start' | '#/songs' | `#/practice/${string}` | `#/results/${string}`

export interface Settings {
  tolerance: Tolerance            // default 50
  delayMs: number | null          // total scoring delay 0..1500, default null = as reported; applied with pitch.setDelayMs at app start
  headphoneSheetSeen: boolean
  installHintSeen: boolean
  roles: RoleId[]                 // last selection
  mode: Mode                      // last voicetrack mode, default 'all'
}
export const settings: { get(): Settings; set(p: Partial<Settings>): void; reset(): void }  // localStorage key "gu.settings"
```

## Routing

- Start route shown when vault state is `locked` or `password-changed`. Any other route redirects there.
- Unlocked app start: songs. Practice and results routes need a ready song, else redirect to songs.
- Results route: only with `features.results` (`src/app/features.ts`, off for now) and the live session of that song; otherwise practice of that song.

## PWA

- Web manifest: name and short name `LKG Musical 2026` (also `apple-mobile-web-app-title` and page title, the name shown when installed), `display: standalone`, theme and background `#1F5FAB`, icons 180/192/512 generated by `tools/make_icons.py` from `public/logo.png`: the cross on white, the year as `20` over `26` left of the stem (Chrome badges the bottom right corner), all content inside the maskable safe circle (80 % diameter); 192 and 512 also listed with `purpose: maskable`, 180 is the `apple-touch-icon`.
- Service worker precaches app shell (html, js, css, fonts, icons). `content/` never cached by the worker; library handles it.
- Update: new worker installs, waits. On next app launch it activates. Toast `Neue Version geladen` for 4 s. Never reload or prompt during practice.

## Settings sheet

Opened from the gear button on songs and practice screens. Items, top to bottom:

1. `Toleranz`: segmented `Leicht (75 Cent)` / `Normal (50 Cent)` / `Streng (30 Cent)`.
2. `Verzögerung`: slider 0…1500 ms, step 10, value shown as `{n} ms`; while `delayMs` is null it shows the reported sum (round10 of a + b) as `{n} ms (automatisch)`. Moving it sets `delayMs` and `pitch.setDelayMs`. Help text: `Zeit vom Klang im Kopfhörer bis zum Mikrofon, für die Bewertung. Am besten messen lassen.` Read-only below: `Vom Browser gemeldet: Wiedergabe {a} ms · Mikrofon {b} ms` (`engine.latency()`, `pitch.inputLatency()`, rounded; the mic value is 0 until the mic ran).
3. `Verzögerung messen`: button under the measured line, opens the calibration panel (see Latency calibration).
4. `Mikrofon`: select, `Automatisch (eingebautes Mikrofon)` (`micDeviceId` '') plus every audio input by label (`Mikrofon {n}` while labels are hidden before permission). Saves `micDeviceId`; `pitch.setDevice` restarts a running mic on it.
5. `Mikrofon testen`: button starts pitch engine, shows level bar and detected note name, stops on sheet close.
6. `Kopfhörer`: text `Bitte mit Kopfhörern üben, sonst hört das Mikrofon die Aufnahme mit.` and tip `Tipp: Miss für jeden Kopfhörer einmal die Verzögerung (Einstellungen, „Verzögerung messen“). Dann passen Noten und Bewertung zu dem, was du hörst.`
7. `Sperren und Daten löschen`: red button, confirm dialog `Alle Lieder und Ergebnisse werden von diesem Gerät gelöscht. Fortfahren?` with `Löschen` / `Abbrechen`. Confirm calls vault.lock, then route start.

## Latency calibration

Measures the delay from a sound in the headphones to its pitch frame, instead of guessing `Verzögerung`. Module `src/core/calibration.ts`: pure detection and statistics plus a small runner; the settings sheet shows the panel.

| id | text |
|---|---|
| calButton | `Verzögerung messen` |
| calHelp | `Sag „ta“ genau mit jedem Klick – oder halte den Kopfhörer ans Mikrofon.` |
| calRunning | `Messung läuft …` |
| calCancel | `Abbrechen` |
| calResult | `Gemessen: {n} ms (±{s} ms)` |
| calFailed | `Nicht eindeutig – bitte nochmal.` |

- Runner: pauses playback, starts the pitch engine with `songTime` = playback AudioContext time (`engine.ctxTime()`), so frame `at` is on the click clock. After a 1 s count-in, 12 clicks (1 kHz, 20 ms) every 1 s; the first 4 are warm-up to find the rhythm and not measured via `engine.click(at)` on the playback context (real output path). Collects frames until 0.5 s after the last click. Cancel or closing the sheet stops pending clicks and the mic; a mic the practice screen had running is restarted with its own clocks.
- Onsets: a frame is an onset when its `rms` exceeds max(4 × quiet floor, 0.01) after at least 80 ms below that threshold. Quiet floor = running average of the frames below the threshold. Resolution = one hop.
- While running: `calRunning`, the mic level bar (as in `Mikrofon testen`, `pitch.level()` every 50 ms) so the user sees the phone hears them, and `calCancel`.
- Matching: each click takes its first onset from 100 ms before to 900 ms after it (Bluetooth delays fit; later would be the next click's); delay = onset `at` − click time. Longer delays only by hand on the slider.
- Result: median of the delays, spread = median absolute deviation. Fewer than 5 of the 8 measured clicks matched or spread over 40 ms: `calFailed`.
- Delay: `delayMs = round10(median)`, clamped to 0…1500. It replaces the reported latencies (they can be far off). Saved, applied with `pitch.setDelayMs`; the slider shows it.
  `[@test] ../tests/steps/calibration.steps.ts`

```gherkin
Feature: Latency calibration
  Scenario: onset after quiet
    Given quiet frames at rms 0.002 until 1.000, loud frames at rms 0.1 until 1.100, quiet until 1.150, loud until 1.200, quiet until 1.300, loud until 1.350
    When I detect onsets
    Then the onsets are 1.000 and 1.300

  Scenario: too faint to count
    Given quiet frames at rms 0.0001 until 1.000, loud frames at rms 0.003 until 1.100
    When I detect onsets
    Then there are no onsets

  Scenario: clicks matched to their first onset
    Given clicks at 1.0, 2.0, 3.0, 4.0 and onsets at 0.95, 1.2, 2.45, 2.6, 4.85
    When I match them
    Then the delays are -0.05, 0.45 and 0.85

  Scenario: median and spread
    Given delays of 100, 110, 120, 130, 140, 500 ms
    Then the result is 125 ms with spread 15 ms

  Scenario: too few clicks
    Given delays of 100, 110, 120, 130 ms
    Then the result is not clear

  Scenario: too noisy
    Given delays of 100, 150, 200, 250, 300 ms
    Then the result is not clear

  Scenario: a human spread still counts
    Given delays of 120, 150, 180, 210, 240 ms
    Then the result is 180 ms with spread 30 ms

  Scenario: delay from the measurement
    Then a measured 156 ms gives delay 160
    And a measured 123 ms gives delay 120
    And a measured -40 ms gives delay 0
    And a measured 1600 ms gives delay 1500
```
